# 开发规范

## 1. 工作流程

1. 从 Issue 或明确需求开始，记录范围、风险和验收条件。
2. 修改前确认受影响的前端页面、API、权限和数据库表。
3. 小步实现，避免把无关重构混入功能变更。
4. 执行与风险匹配的检查。
5. 更新 CHANGELOG 和必要文档。
6. 在 PR 或交付说明中列出修改文件、测试结果、限制和回滚方法。

## 2. 优先级定义

- `P0`：安全越权、数据损坏、交易错误或生产不可用，立即处理。
- `P1`：核心功能阻塞、明显错误或上线前必需项。
- `P2`：维护性、体验和一般性能问题。
- `P3`：增强功能和长期优化。

## 3. Issue 建议格式

标题：`[优先级][模块] 动词 + 问题或目标`

正文至少包括：

- 背景和现状；
- 工作范围与非目标；
- 验收条件；
- 安全、数据和兼容性风险；
- 测试要求；
- 文档更新要求。

## 4. 代码评审清单

- 权限是否最小化，普通用户是否可能调用管理员功能？
- 输入是否经过格式和业务校验？
- SQL 是否参数化，事务是否绑定同一连接？
- 库存、金额和订单状态是否保持一致？
- 错误响应是否泄漏内部信息？
- 前端是否使用真实 API，并处理加载、失败、空数据和无权限？
- 是否加入了模拟登录、固定密码、默认密钥或硬编码服务地址？
- 测试是否覆盖正常、异常和越权路径？

## 5. API 约定

- 资源使用复数名词，例如 `/api/products`。
- 固定路径先于参数路径，例如 `/stats` 必须先于 `/:id`。
- HTTP 状态码与业务结果一致。
- 分页参数统一使用 `page` 和 `pageSize`。
- 时间使用 ISO 8601；金额接口明确币种和最小单位。
- 新接口优先返回 `{ code, message, data }`。

## 6. 环境约定

至少区分：

- local：本机开发；
- test：自动测试；
- staging：集成和验收；
- production：生产。

真实配置仅通过环境变量或秘密管理服务注入。仓库只保存 `.env.example`，不得保存真实 `.env`。

## 7. 版本与变更记录

- 修复和功能在 `CHANGELOG.md` 的 `Unreleased` 下记录。
- 正式发布时创建版本号、发布日期和 Git tag。
- 数据库变更、部署和回滚结果使用相应模板存档。
- 未执行的检查必须明确写为“未执行”，不能留空或写“通过”。
