## 2. 现状（正式库只读核查，近 91 天已付款 POS 销售）

### 2.1 商品分类

| 项目 | 销售额占比 | 说明 |
| --- | --- | --- |
| 品类和功能都已识别 | 75.1% | |
| 有品类、没有功能 | 23.9% | 桑基图中的“无明确功能”。主要是成人奶粉 6.8%、蜂蜜 4.9%、面部护理 2.1%、洗发护发 1.9%、羊奶粉 1.1%、香皂 1.0% |

“无明确功能”分三种情况：

| 情况 | 例子 | 处理 |
| --- | --- | --- |
| 本来没有保健功能 | 洗发水、香皂、零食、普通奶粉 | 属正常，不应算“漏识别”，桑基图中应按品类显示 |
| 规则漏识别 | 蜂蜜名称只写“UMF18+”“MGO 400+”，没有“蜂蜜”字样；“Rosehip Oil”“AGE treatment”没有抗衰关键词 | 补充识别规则 |
| 品类本身没认出来 | 新品牌、缩写名称 | 人工指定品类 |

“其他细分 37.6%”不是 37.6% 没分类：桑基图第三层只单独画前 10 个功能细分，其余细分和“无明确功能”商品都合并显示为“其他细分”。

## 3. 目标

1. 销售额中“漏识别”（不含本来没有保健功能的商品）降到 5% 以下，品类未识别降到 0.5% 以下。
2. 我们的每个品类能对应到魔镜的平台类目，市场分析可以显示“店内与市场”同期对比。
3. 行业新闻每天自动更新，每条有来源、链接、日期，并标出与店内哪些品类有关。
4. 为 AI 销售报告准备准确的店内数据和市场数据；AI 接入另行确认，不在本需求内。

### 3.1 三个模块的关系

| 模块 | 回答的问题 | 数据 | 现状 |
| --- | --- | --- | --- |
| 店铺分析（店铺经营发现） | 本店卖了什么、卖给谁、库存够不够 | POS 销售、库存、商品分类 | 已上线 |
| 外部行情（市场对比、行业趋势） | 市场上同类卖得怎样，行业在关注什么 | 魔镜月度类目与热销数据、RSS 行业新闻 | 新闻待上线；魔镜待开通 |
| AI 产品售卖分析（AI 销售报告） | 本店该进什么、推什么、清什么 | 前两个模块的汇总结果，不含顾客信息 | 未开始，待选定大模型 |

三者通过同一套商品分类连接：店铺分析按品类、功能、门店细分汇总销售；外部行情通过“品类对应表”把本店品类对应到魔镜类目，新闻按同名主题打标签；AI 报告把同一分类下的“店内增速、市场增速、新闻热度、店内库存”放在一起比较，给出进货、推广、清货建议。分类不准，三个模块的结论都会出错，所以先修正分类。

## 4. 范围与规则

### 4.1 第一部分：商品分类修正

| 编号 | 内容 | 规则 |
| --- | --- | --- |
| A1 | 标注表 | 开发从正式库只读导出“无明确功能”和“未识别”的商品，共 512 个，按近 91 天销售额排序（文件 `output/REQ-016/商品分类标注表_近91天.xlsx`）。甲方填写：确认品类、功能、无功能属正常、人群。前约 194 行占待标注销售额的 90% |
| A2 | 规则修正 | 按标注结果修改识别规则，同类商品一起生效（如蜂蜜补充 UMF、MGO、Manuka）；只有个别商品例外时写入该商品的人工品类。规则在查询时计算，不改 POS，不改历史销售 |
| A3 | 本来无功能的商品 | 标为“无功能属正常”的品类，在桑基图中按品类显示（如“洗护用品”“零食”），不再并入“无明确功能”；“无明确功能”只留真正需要处理的商品 |
| A4 | 识别率显示 | 市场分析店铺经营发现显示两个比例（按销售额）：功能识别率、品类识别率；点击可查看未识别的商品并到“分类与标签”指定 |
| A5 | 其他细分说明 | 桑基图“其他细分”悬停或点击时列出合并了哪些细分及各自占比 |
| A6 | 门店细分标签 | 甲方标注表在“开发建议”列为 506 个商品写了标签（如“高级洗发”“香皂/伴手礼”“日常营养”“抗衰”），多数是比二级品类更细的门店细分和“伴手礼”属性。新增商品字段“门店细分标签”（最多 60 字，多个用“/”分隔）。识别品类、功能、人群时，标签与商品名称一起参与识别：标签写“抗衰”“保湿”“护肝”等即识别为对应功能，写“伴手礼”即计入“游客（伴手礼）”。人工品类仍然优先 |
| A7 | 桑基图按细分显示 | 没有功能但有门店细分标签的商品，第二层显示一级品类（如“洗护用品”），第三层显示标签第一段（如“高级洗发”），不再计入“无明确功能” |
| A8 | 日常营养 | 按甲方标注新增功能“日常营养”：奶粉与乳制品，以及标签写“日常营养”的保健品和食品 |
| A9 | 导入 | 开发从标注表生成导入清单，只导入甲方改写过的行；标签与当前品类明显矛盾的行（如奶粉标“蜂蜜”）不导入，列出请甲方确认。门店电脑用管理员账号运行导入脚本，逐个调用接口写入，每个商品写审计日志 |

### 4.2 第二部分：魔镜市场数据

| 编号 | 内容 | 规则 |
| --- | --- | --- |
| B1 | 密钥 | 密钥由甲方写入门店电脑 `.env` 的 `MOOJING_API_KEY`，不进代码库，不经聊天、邮件传送；未配置时市场数据功能显示“未开通”，其他功能不受影响 |
| B2 | 类目对应 | 读取魔镜类目树（`cats_tree`），开发为每个二级品类拟定对应的平台与类目编号（优先天猫国际、京东国际，其次天猫、京东），列出对应表由甲方确认；管理员可在设置中修改。一个品类可对应多个魔镜类目，没有对应的品类不比较 |
| B3 | 每月同步 | 每月先调用 `latesttime` 查魔镜最新数据月份；有新月份时，对已确认的类目各取一次：类目趋势（`trend`，按月，含同比、环比）、热销商品前 20（`hot_items`）、热销店铺前 10（`hot_shops`）。结果存入本系统数据库，页面只读本地数据，不在打开页面时调用魔镜 |
| B4 | 费用控制 | 设置每月调用次数上限；每次调用记录时间、接口、类目、结果；达到上限、余额不足（-411）、当天额度用完（-413）时停止并在页面提示；请求过快（429）时等待后重试，最多 3 次；管理员可手动“重新同步”，同样计入上限 |
| B5 | 店内与市场对比 | 市场分析新增“市场对比”：按品类列出店内近 3 个月销售额变化与市场同期销售额变化、市场均价；标出“市场在涨、店内在跌”和“市场在涨、店内没有这类商品”的品类 |
| B6 | 市场热销品牌 | 每个品类列出市场热销品牌和商品，标出本店是否有该品牌（按品牌名称比对，可人工确认对应关系）；只作参考，不自动加入进货单 |
| B7 | 使用限制 | 魔镜数据只在本系统内部查看，不导出给第三方；每条数据标注“来源：魔镜，数据月份” |

### 4.3 第三部分：行业新闻 RSS

| 编号 | 内容 | 规则 |
| --- | --- | --- |
| C1 | 来源 | 首批 4 个：NutraIngredients（全球）、FoodNavigator-Asia（亚洲）、Campaign Brief（澳新）、StopPress（澳新），由迁移写入。管理员可添加、停用、启用来源（停用后其新闻不显示，记录保留）；只接受网站公开提供的 https RSS 地址，不抓取网页；地址指向内部网络（本机、局域网等）时拒绝读取 |
| C2 | 更新 | 每个来源每天读取一次（`NEWS_FEED_REFRESH_HOURS`，默认 24，设为 0 停止自动读取；只在门店电脑一个服务上开启）；读取失败 1 小时后重试；管理员可“立即更新”。同一链接只保存一次（去掉 utm 跟踪参数后比较）；每条保存标题、摘要（RSS 自带，最多 600 字）、链接、发布日期、来源；超过 90 天的不保存 |
| C3 | 分类标注 | 地区按来源；主题用新闻专用关键词表识别，主题名称与商品功能分类（CR-021）和品类一致，另有“监管与召回”“跨境与中国市场”。不直接套用商品名称规则：商品规则中的 growth、vision、rose 等词在新闻里是普通商业用语，会误标。主题在查询时计算，规则更新对旧新闻即时生效。每个主题显示店内有货商品数（按商品名称识别的功能或品类统计）；不使用 AI |
| C4 | 显示 | 行业趋势模块：近 7 / 30 / 90 天、地区、主题筛选，默认近 30 天；默认勾选“只看与店内相关”（至少一个主题在店内有货），并提示隐藏了多少条，取消勾选可看全部（广告营销类新闻用于活动参考）；点击标题在新窗口打开原网站。市场分析首页卡片显示“本周 N 条 · M 条与店内相关” |
| C5 | 读取失败 | 某个来源读取失败只记录并显示“最近一次成功时间”，不影响其他来源 |
| C6 | 中文翻译（待确认，未开发） | 新增新闻时翻译一次标题和摘要并保存，页面默认显示中文、可切换原文；只翻译新闻文字，不发送店内数据。候选：翻译接口（如 DeepL API Free，有每月免费额度，以官网为准），或与 AI 销售报告共用大模型接口（可同时生成“与本店的关系”一句话）。甲方确认供应商后开发 |

### 4.4 不在本需求范围

- AI 销售报告、AI 新闻摘要：等甲方选定大模型供应商与每月费用上限后另行变更，届时以本需求的店内数据、市场对比和新闻作为依据。
- 蝉妈妈、巨量引擎、小红书聚光与蒲公英、亚马逊数据工具。
- 价格建议：市场均价只作参考，系统不建议售价。

## 5. 数据表

迁移各自写明升级说明与回滚语句：阶段 2 `202611110001_industry_news`（`news_sources`、`news_items`，已完成）；阶段 1 `202611110002_product_store_label`（商品表加 `store_label`，已完成）；阶段 3 另建迁移（魔镜相关四张表）。

| 表 | 内容 |
| --- | --- |
| `market_category_mappings` | 本店二级品类 → 魔镜平台、类目编号、类目名称；是否已确认、确认人 |
| `market_category_months` | 每个魔镜类目每月的销售额、销量、均价、商品数、店铺数、同比、环比、数据月份、取得时间 |
| `market_hot_entries` | 每个类目每月的热销商品与热销店铺：名次、名称、品牌、店铺、销售额、销量、价格、链接编号 |
| `market_api_calls` | 每次调用：时间、接口、参数、结果代码、是否计费、错误信息（不保存密钥） |
| `news_sources` | RSS 来源：名称、地址、地区、是否启用、最近成功与失败时间 |
| `news_items` | 新闻：来源、标题、摘要、链接（同一组织内唯一）、发布日期；主题与地区在查询时计算，不存表 |
| `products.store_label`（新增字段） | 门店细分标签，可为空，最多 60 字 |

分类修正（第一部分）不新增表：规则改在代码中，商品使用门店细分标签和现有人工品类。设置的新增和修改写审计日志。

## 6. 接口

均需登录并有该门店权限；设置与手动同步仅管理员。

| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/market/overview?storeId=` | 市场对比：品类店内与市场变化、热销品牌、数据月份、开通状态 |
| `GET /api/v1/market/mappings`、`PATCH /market/mappings/:id` | 类目对应表查看与修改 |
| `POST /api/v1/market/sync` | 手动同步（计入每月上限） |
| `GET /api/v1/market/usage` | 本月调用次数、上限、最近错误 |
| `GET /api/v1/news?storeId=&days=&region=&topic=` | 行业新闻（days 为 7、30、90） |
| `GET/POST /api/v1/news/sources`、`PATCH /news/sources/:id` | RSS 来源查看、添加（添加后立即读取一次）、改名、改地区、停用与启用 |
| `POST /api/v1/news/refresh` | 立即读取全部启用的来源 |
| `POST /api/v1/management/product-categories/label?storeId=` | 写入或清除一个商品的门店细分标签（管理员，写审计日志）；“分类与标签”列表同时返回标签 |

## 7. 数据安全与合规

1. 发给魔镜的只有平台、类目编号、月份等查询参数，不发送本店销售、顾客或员工信息。
2. 密钥只在门店电脑 `.env`；调用记录不保存密钥。
3. 只使用魔镜正式接口和网站公开的 RSS；不抓取需要登录或禁止抓取的网站。
4. 外部数据只供内部经营参考，页面标注来源与日期。

## 9.1 上线（阶段 1 门店细分标签）

| 步骤 | 内容 |
