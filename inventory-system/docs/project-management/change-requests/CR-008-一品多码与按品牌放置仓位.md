# 需求变更单：一品多码多名统一档案、按品牌批量放置仓位

| 项目 | 内容 |
| --- | --- |
| 变更编号 | CR-008 |
| 关联需求 | REQ-012（盘点）、REQ-013（POS 商品对应）、CR-006（同款合并）、仓位管理 |
| 提出日期 | 2026-10-27（客户反馈） |
| 状态 | F2、F4、F5、F7 已推送（待 Windows 上线）；F8 开发完成（待推送）；F1、F3、F6 待确认 |

## 1. 变更来源

| 日期 | 渠道 | 内容摘要 |
| --- | --- | --- |
| 2026-10-27 | 客户反馈 | 同一商品可能有多个到期日、多个条码，名称也可能不同，但销售时是同一个商品；盘点点完后系统仍提示该商品的其他档案有库存。此前的做法是让 POS 统一用一个条码代替 |
| 2026-10-27 | 客户反馈 | 仓位按品牌统一放置，希望按品牌一次选择仓位，不再逐个商品、逐个批次分配 |
| 2026-10-27 | 客户反馈 | 先做批量设置仓位；设置后扫码入库、查询日期（库存查询、临期预警）显示仓位；管理员和员工都可修改仓位（后期按空间调整） |
| 2026-10-30 | 客户反馈 | 库存盘点页同一商品出现多个不同名称的档案（例：红印牙膏多种写法），条码和到期日不同但实际是同一商品；要求在库存盘点和经营管理的库存页面直接合并 |
| 2026-10-30 | 客户反馈 | 合并后同一商品的多个到期日期在盘点页分成多行，每行都重复商品名，看不出合计，现场核对总数不方便；要求一行显示商品合计，下面按日期分别显示数量 |

## 2. 现状分析（开发库 `sunshine_dev_20261027`，数据截至 2026-10-27 14:43）

| 项目 | 现状 |
| --- | --- |
| 多到期日 | 已支持：一个商品下多个批次 |
| 多条码 | 已支持：一个商品可挂多个条码（目前 38 个商品有多条码） |
| 多名称 | 部分支持：商品名、中文名、英文名，以及 POS 名称（对应关系中保存） |
| 重复档案的来源 | 每小时的 POS 商品对应：POS 里出现系统没有的条码时，按 POS 名称新建一个商品档案，而不是挂到已有商品上 |
| 同名重复 | 同名（忽略大小写、空格、标点）的档案组 40 组 95 个；其中“一份已点、另一份仍有库存”的为 0（已在 10-26 处理） |
| 不同名重复 | 未盘点且有库存的档案 445 个（17,312 件）。按品牌、规格数字、名称相似度试算，36 个疑似与已点商品重复，但人工抽查发现大量是同品牌不同口味（如 Bruntwood Lane 香皂各香型），不能自动合并 |
| 仓位 | 已有仓位功能，但按“批次 + 件数”分配，且 POS 销售不会更新仓位件数；目前仓位 0 个、分配 0 条 |
| 品牌 | 商品档案的品牌字段全部为空，页面上的品牌是按名称推测的 |

## 3. 变更内容

| 编号 | 变更 | 规则 |
| --- | --- | --- |
| F1 | POS 新条码挂到已有商品 | 每小时对应时，POS 出现新条码：先按名称（同名规则：忽略大小写、空格、标点，swiss 视同 swisse）在已有商品的名称、中文名、英文名、POS 名称中查找；恰好找到 1 个时，把新条码挂到该商品，不新建档案；找到 0 个或多个时仍按原规则新建，并列入 F3 的待确认清单。写审计 |
| F2 | 库存页面直接“合并同款” | 入口：库存管理 → 库存盘点（每个商品第一行，电脑表格与手机卡片）；经营管理 → 库存经营（每行操作）。仅管理员可见（合并接口要求门店管理员）。沿用 CR-006 合并：搜索名称或条码，勾选同一商品的其他档案；库存默认“以保留商品为准”（同一批货重复点数），可选“库存相加”（不同的货）。条码、POS 对应、销售记录、仓位转入保留商品，旧档案停用不删除，写库存流水与审计。合并后刷新当前页面 |
| F3 | 疑似重复清单 | 盘点页增加“疑似同款 N 组”入口：列出同品牌、同规格、名称相近，且一份已点、另一份未点但有库存的档案组。每组可“合并”或“不是同款”（记住，不再提示）。只提示，不自动合并 |
| F4 | 商品仓位改为“存放位置” | 每个商品在本店有一个存放位置（不再按批次和件数分配）；库存台账、盘点页、进货单显示位置。原“批次 + 件数”分配保留数据但不再作为主要操作 |
| F5 | 按品牌批量放置 | 仓位管理增加“按品牌放置”：选择品牌（显示该品牌商品数），或输入关键词（如 帕氏、swisse）；列出命中的商品，默认全选，可去掉个别商品；选择仓位后一次保存。已有位置的商品标出，确认后覆盖。写审计（记录每个商品原位置与新位置） |
| F7 | 公网访问地址 | 迁移到 Windows 后公网地址变为 `node.tail10ff0a.ts.net`；接口来源白名单原先只认 Mac 地址，会导致经公网登录、保存失败。改为接受本 Tailscale 网络内（`*.tail10ff0a.ts.net`）的 HTTPS 地址 |
| F8 | 盘点页按商品分组 | 库存管理 → 库存盘点：同一商品有多个到期日期时，先显示一行商品汇总（商品名、“合并同款”、日期个数、系统合计件数、已填实际数量合计），下面每个到期日期一行，分别显示系统数量并分别填写实际数量和原因。只有一个日期的商品仍为一行。手机端每个商品一张卡片，卡片头部显示合计，卡片内按日期分别盘点。仅改显示，盘点仍按批次提交，接口与数据不变 |
| F6 | 品牌整理 | 品牌按名称自动识别（沿用进货单品牌规则并扩充）；按品牌放置时可直接修正识别错误的品牌，保存到商品档案，后续页面统一使用 |

## 4. 影响评估

| 方面 | 影响 |
| --- | --- |
| 数据库 | F4 新增 `store_products.location_id`（可为空，引用仓位）；F3 新增“不是同款”记录表。迁移只新增，不修改已有数据；回滚为删除新增字段和表 |
| 库存 | F1 减少新的重复档案；F2、F3 的合并写库存流水和审计，与 CR-006 相同 |
| POS 扣库 | 合并或挂码后，POS 销售统一扣到保留的商品 |
| 仓位 | 原批次分配数据为 0 条，改为商品位置无数据迁移负担 |
| 上线 | 需要执行数据库迁移；先在开发库验证，再在 Windows 正式环境执行 |
